01 — the context

An agency paying twice for the same button

Nerdbug builds software for clients out of Atlanta and Lagos. Every engagement started from a blank Figma file, which meant every engagement rebuilt the same date picker, the same table, the same empty state — slightly differently each time.

The cost wasn't obvious because it never appeared as a line item. It showed up as rework: engineers rebuilding components they'd built before, designers answering questions that had been answered before, and QA finding the same accessibility failures on every project.

02 — the problem

Design systems fail for social reasons, not technical ones

I'd seen the standard failure before: someone builds an exhaustive library, publishes it, and nobody uses it. The components are technically fine and nobody trusts them — because the first time a designer needs a variant that doesn't exist, they detach, and once you've detached once you never go back.

“A design system isn't adopted because it's complete. It's adopted because the parts that exist are reliable enough to stop checking.”

So the design problem wasn't coverage. It was credibility.

03 — what I decided

Three calls about scope and governance

decision 01

Twelve components, properly. Not forty, roughly.

I audited three recent client projects and counted which components actually appeared. Twelve covered most of every build. I scoped to those and specified them exhaustively — every state, every breakpoint, every focus and error condition, with accessibility built in rather than bolted on.

what it costDesigners worked off-system for months on anything outside the twelve, and I had to keep saying no to reasonable requests for a thirteenth. But the twelve were trusted, and that's what got the system used at all.
decision 02

Tokens named for intent, not appearance

surface-raised, not grey-100. Client work means the palette changes every engagement; a system named after its colours has to be rewritten each time, and one named after its intentions doesn't.

what it costA steeper learning curve for junior designers, who find a literal colour name easier to reach for. I wrote the documentation around this and it's still the thing I explain most often.
decision 03

A written route for adding to the system, on day one

Most systems get a contribution process after the first fight about an unapproved component. I wrote it before launch: how to propose, who decides, and how long it takes.

what it costProcess overhead on a small team that would rather just build. It's the least popular thing I introduced and the reason the system still holds.
04 — what happened

The numbers, and the caveats

  • −35%Development rework, from the engineering lead's estimate rather than a tracked metric — I'd treat it as directional.
  • −30%Design iteration cycles before stakeholder approval.
  • 7Client products now building on the system.
05 — in hindsight

What I'd do differently

I built for designers first and engineers second. The Figma library was excellent months before the code side caught up, which meant handoff still involved translation — exactly the cost the system existed to remove. I'd pair with an engineer from day one now.

I'd also start the mentoring earlier. I taught the system after building it; the two junior designers would have adopted it faster if they'd helped decide what went in.
